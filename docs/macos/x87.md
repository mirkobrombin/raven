# x87 in the translator

`native/translate/` runs x87 code. This note records what x64 Windows code uses of x87, the guest state, the precision decision and
its measurements, how the instructions run, what x86 silicon does where Rosetta does not, the tests and their results, a short
performance check and the open items. SSE and SSE2 are in [sse.md](sse.md); AVX and MMX come later.

Labels are those of [translation.md](translation.md): **PROVEN** (a command produced the result), **INFERRED** (derived; the missing
check is named), **NOT verified**. MacBook Air M5 (Mac17,3), macOS 27.2.1, Xcode 27.2, llvm-mingw 20261104. The x86 reference is an
AMD EPYC 9V45 (GitHub Linux x86_64 runner, the private raven-macos-bench repository, runs 44415784342, 44419865688, 44420484491
and 44422191578); Rosetta runs the same cases on every build, and where the two disagree the tests take the EPYC's result.

What this says:

- **MSVC x64 code has no x87.** Notepad++ is built with MSVC, whose `long double` is `double`, and Microsoft's x64 calling
  convention page (learn.microsoft.com/en-us/cpp/build/x64-calling-convention, 2025-03-19) says the x87 register stack is unused and
  all floating point is done in the XMM registers. PROVEN for Notepad++ as a lower bound (0 reachable); that MSVC never emits it is
  INFERRED from the page and that count.
- **x64 x87 is mingw code with an 80-bit `long double`**: its math library, `long double` I/O in libc++, compiler-rt, libomp and
  winpthread. `__mingw_pformat` loads a `double` argument with `fld qword ptr`, so a mingw `printf("%f")` with
  `__USE_MINGW_ANSI_STDIO` goes through x87 (PROVEN: `fld qword ptr [r13]` at 0x638 of `lib64_libmingwex_a-mingw_pformat.o`).
- **Not found outside data:** fbld, fbstp, fisttp, fnsave, frstor, fxsave, fxrstor. fbld and fbstp are decoded but not run; the
  others are run because the oracle needs them (fnsave and frstor) or cost nothing (fisttp).
- **Transcendental instructions** are 31 of the 4093 in `libmingwex.a` (logl, expl, atan2l, sinl and friends) and absent from the
  DLLs: they are left for later (open items).
- **llvm-mingw has no `ucrtbase.dll`**: Microsoft's UCRT is a proprietary binary and was not examined. The `libucrt.a` counted above
  is mingw's import and helper library.
- **32-bit (WoW64) code** uses x87 for every `float` and `double`; that is out of scope here (only x64 code is translated).

The decoder test counts x87 per source (`x86_decoder_test`, PROVEN at the end): `x87_instances.o: 4000 x87 instructions, 4000 with
semantics (100.0%), 3706 translated (92.7%); without: fbld 88, fbstp 75, f2xm1 24, fyl2x 20, fsincos 17, fsin 15, fptan 15, fyl2xp1
14, fpatan 13, fcos 13`. "Translated" there means the runtime runs it (`translates()`).

## Guest state

- **`CpuState::x87`** (`X87State`, cpu_state.h): FCW, FSW (TOP in bits 13:11), the abridged tag byte (bit n set: Rn holds a value),
  FOP, FIP, FDP and the eight 80-bit registers. The fields follow the FXSAVE image's first 160 bytes, so a CONTEXT `FltSave` copy is
  a field-by-field copy, except that `st` holds the **physical** registers R0-R7, not ST(0)-ST(7): ST(i) is R((TOP + i) mod 8). A
  push or pop then moves TOP and a tag and no data, and MMX (below) is a plain alias.
- **Kept across exits by construction.** Translated code never touches it: only the host core reads and writes it, between runs, in
  this process and for a vCPU alike (the CpuState lives in memory both see). PROVEN by the oracle passing in both runners, where every
  case has several exits (see the execution model).
- **Default:** FCW 0x27f (precision 53 bits, round to nearest, all exceptions masked), FSW 0, every register empty.
  - Microsoft's x64 calling convention page lists FCW bits 0-12 as all exceptions masked, precision control 10B (double), rounding
    control 0, at "the start of program execution", and FCW as nonvolatile across calls. That a new thread starts with the same is
    INFERRED (the page says program start; no Windows thread was probed).
  - mingw programs change it at once: `__tmainCRTStartup` calls `fpreset` (`CRT_fp10.o`, the default), which runs `fninit`: FCW 0x37f,
    64-bit precision. PROVEN by linking `hello.c` with `x86_64-w64-mingw32-clang -O1` and disassembling: `140001188: call
    0x140001b60 <fpreset>`, `140001b75: fninit`. So the code that actually uses x87 (the corpus above) runs at PC = 64 bits.
- **MMX** (not implemented) is designed in: MMn is the significand quadword of Rn; an MMX write sets that register's exponent field to
  0xffff, TOP to 0 and every tag valid; emms empties the tags. With physical registers that is a direct alias, and translated MMX
  code could keep MMn in vector registers if it spills them to `CpuState::x87.st` before any x87 exit.

## Precision: the decision and its numbers

Arm has no 80-bit floating point. Three options were weighed:

- (a) a software 80-bit implementation, exact and slower per instruction;
- (b) doubles, fast;
- (c) a hybrid: doubles where provably exact, (a) otherwise.

**Decision: (a).** Every x87 instruction runs in an integer implementation of the 80-bit format
(`native/translate/x87.cpp`): 64-bit significand, 15-bit exponent, all four rounding controls, all three precision controls (and the
reserved one, which x86 treats as 64 bits), denormals, pseudo-denormals, unnormals, pseudo-infinities and pseudo-NaNs, every
exception flag and C1. No host floating point is used, so FPCR plays no part; the double arithmetic of the measurement below exists
only in the separate `x87_measure` build (`RAVEN_X87_DOUBLES`), not in the library the runtime links.

Why not (b) or (c), measured on the oracle's cases (`x87_measure ... --doubles`, which runs add, sub, mul, div and sqrt in host doubles
and counts the cases whose result differs from x86's in a register or memory, the status word set aside):

| Family, precision control | Cases | Differ in a value | Differ at all |
|---|---|---|---|
| arithmetic, PC 24 | 234 | 87 | 94 |
| arithmetic, PC 53 | 945 | 204 (21.6%) | 363 |
| arithmetic, PC 64 | 1081 | 346 (32.0%) | 406 |
| arithmetic, PC reserved (01) | 140 | 43 | 50 |
| sequences (loads, arithmetic, compare, store), PC 53 | 153 | 31 | 50 |
| sequences, PC 64 | 182 | 55 | 68 |

PROVEN (that command). The cases lean on edges (64-bit significands, exponents beyond double's, denormals), so real code differs
less often, but the point stands: even at PC = 53 a double is not the x87 result once an operand has more than 53 significant bits or
an intermediate leaves double's exponent range (the 15-bit exponent still applies at PC = 53), and the code that uses x87 on x64 runs
at PC = 64 (mingw's `fninit`), where doubles are wrong for most inexact operations. A double fast path (c) would need a check per
operation that both operands fit 53 bits and double's exponent range and that PC is 53, plus exact PE, C1 and UE; that check costs
about what the exact path does here (next paragraph).

What exactness costs:

- In the core alone, `x87_measure ... --core-time` times the 2828000 single-register arithmetic instructions of the oracle (state
  reload included): exact 280.0 ns each, doubles 235.0 ns each. PROVEN (measured before x87_measure was split off as its own build,
  with the same code).
- A scratch program over the core (not in the repository, so PROVEN only as that run's output) times one instruction without the
  reload: fmul 33 ns, fadd 41 ns, fdiv 59
  ns, fsqrt 341 ns (a bit-by-bit square root), and the decoder about 50 ns per instruction.
- Against that, an exit and a return to translated code cost about 0.7 µs in this process and 2-3 µs in a vCPU (the workloads below).
  The exits, not the arithmetic, set the cost: (b) would save some 15% of the core's time and none of the exits.

No approximation is presented as exact: the core matches the EPYC to the bit on every oracle case it runs (PROVEN below); that it is
exact on inputs outside the cases is INFERRED from the implementation (integer arithmetic carrying every bit to the rounding step),
not proven. The instructions it does not implement exit as unsupported instead of running approximately.

## How it runs

- **The translator does not emit x87.** A block ends before an x87 instruction the core implements with `ExitReason::x87` (rip is
  that instruction). An unimplemented one (the transcendental eight, fbld, fbstp) ends the block as unsupported, as before.
- **`Runtime::Thread::run`** handles the exit: it decodes the instruction at rip and runs it with `x87_execute`, then the next, until
  one is not x87 (that one goes back to translated code). A `fault` result (a waiting instruction with an unmasked exception
  pending, where x86 raises #MF) returns `ExitReason::fault` with rip at that instruction and `CpuState::exit_info` set to
  `FaultKind::x87`, so a later STATUS_FLOAT_* mapping need not decode the instruction again (FSW and FCW say which exception);
  hlt and ud2 in translated code give `FaultKind::instruction`. PROVEN by both x87 tests, which check it, and a ud2 case; and by the
  `pending` cases: the eight waiting ones raise SIGFPE on the EPYC and stop with that fault here; fnstsw, fnstcw, fnclex and fninit
  run on both. If the first instruction at rip cannot be run after all (its code went away), the exit returns `unsupported` instead
  of looping.
- **Memory operands** go through `GuestMemory::read` (new) and `write`, so the same core runs for this process (plain memory) and
  for a vCPU (`Vm::read` and `Vm::write`, `VmProcess` also handling writes to watched code). RIP-relative operands use the next
  instruction's address and index registers are scaled (PROVEN: the `addressing` cases). Segment overrides add `fs_base` or
  `gs_base` after a 32-bit address is truncated: NOT verified (no case uses fs:, gs: or 67, which cannot be run in this process
  with 64-bit host addresses), and the translator's own address code adds the base before truncating, so the two disagree on an
  `addr32 fs:` operand.
- **EFLAGS** (fcomi, fucomi and their pop forms): the core writes `CpuState::nzcv` (Z = ZF, C = not CF, N = V = 0) and the PF and AF
  sources (AF clear), the form block boundaries use. fcmov reads them the same way.
- `translator_version` is 5, since blocks that used to end as unsupported now end with the x87 exit.
- **This is temporary.** The final form calls the same core from translated code without leaving it: an x87 instruction becomes a
  call through a CpuState slot, and in a vCPU that slot points at the core built as freestanding code in guest memory. Loads,
  stores, fxch and constants can be emitted inline then (they move 80 bits and tags, no arithmetic). Not done: it is generator work.

## Semantics

Each rule below comes from the EPYC's results and the oracle holds the core to it on the cases that exercise it; where the line
says so, Rosetta does something else.

- **Rounding.** Results are rounded once, at the precision control's bit (24, 53 or 64; 01 behaves as 64), with the 80-bit exponent
  range at every precision; below the smallest normal they are denormalised and rounded at the same bit positions. fst to m32 and
  m64 rounds to the destination's precision and range instead; frndint and fist round to an integer as RC says; fadd and friends
  with a zero operand still round the other operand to PC.
- **Tininess is detected after rounding**: a result whose exact value is below 2^-16382 but rounds to it raises no UE when masked.
  PROVEN: with the rule flipped to before rounding, `tininess` failed 24 of its then 80 cases; as committed, none.
- **C1** is 1 when an inexact result was rounded up in magnitude, 0 otherwise, 1 on a stack overflow and 0 on an underflow. fcomi,
  fucomi and fcmov leave it as it was. That is the EPYC's behaviour; Intel's manual may describe C1 as cleared by fcomi, and no
  Intel core was run (NOT verified). Rosetta's C1 differs from the EPYC's in 300 cases (the table below).
- **Unmasked exceptions.** IE, DE and ZE unmasked stop the instruction before it writes or pops anything; OE and UE unmasked leave
  the result in a register with its exponent wrapped by 24576, and for fst to memory leave memory unchanged and report OE or UE
  without PE; UE unmasked is reported for a tiny result even when it is exact. Any unmasked flag sets ES and B; Rosetta never sets
  them (264 cases in the table below). Compares still set C3 C2 C0 (or ZF PF CF) to unordered when IE is unmasked, and do not pop.
- **DE** is reported only where the operation computes with a finite denormal: not beside a NaN, an unsupported value or an empty
  register, not when the operation is invalid or divides by zero, not for fst, fist or fisttp, not for a negative denormal's fsqrt.
- **Stack faults.** A push onto a full register raises IE and SF with C1 = 1, and the masked response pushes the indefinite
  (0xffff c000000000000000) without reporting what the value's own conversion would have raised. Reading an empty register raises IE
  and SF with C1 = 0, and the masked response uses the indefinite. fcmov with an empty operand loads the indefinite whatever the
  condition.
- **Pops and frees leave the register's bits** and only mark it empty. Rosetta writes the indefinite into it (1314 cases).
- **NaNs:** an SNaN operand raises IE and is quieted; of two NaNs the result is the one with the larger significand, the positive
  one on a tie; a QNaN wins over an SNaN. Unsupported formats raise IE and give the indefinite. fld m80 and fld st(i) load an SNaN as
  it is, without IE; fld m32 and m64 of an SNaN raise IE, and of a denormal DE.
- **fldcw, fldenv and frstor** keep bits 0-5, 8-12 of the control word and set bit 6 (FCW = value & 0x1f3f | 0x40), and set ES and
  B from the loaded flags and masks, not as stored. PROVEN by the `environment` cases: a status word with IE set, IE unmasked and ES
  clear makes the next fwait or fadd raise #MF on the EPYC and `fnstsw ax` read 0x8081; ES set with every flag masked raises
  nothing.
- **fnstenv** stores FCW, FSW and the full tag word (00 valid, 01 zero, 10 special, 11 empty, computed from the registers), each
  padded to 32 bits with 0xffff, then masks every exception (Rosetta does neither). fnsave also stores the eight
  registers from ST(0) and then does what fninit does. The pointers and the opcode are written as 0 (not compared).
- **fprem and fprem1** are exact. When the exponents are 64 or more apart the reduction is partial (C2 = 1, C0 C1 C3 = 0), by a
  multiple of ST(1) times a power of two leaving an exponent difference of 32 + (difference mod 32). Otherwise C0, C3, C1 are the
  quotient's bits 2, 1, 0. Without a quotient (a fault, an invalid operand, a NaN) C0 and C3 stay and C1 and C2 clear. A
  pseudo-denormal returned as it is comes back normalised.
- **fxtract** with a full stack raises the overflow before anything and leaves two indefinites; of a zero it raises ZE and gives -inf
  and the zero.
- **ffreep** frees ST(i) and pops. Rosetta raises SIGILL on it (the oracle records the signal and continues).

## Performance check

`hvf_bench_run.py build-macos-hvf RESULTS 5 .../quiet/thermal ldot,lpoly`, with `native/hvf/testdata/x87_workloads.c`:

- **ldot:** a dot product of 512 doubles in `long double`, 8 times: `fld`, `fmul`, `faddp` per element, unrolled by 2, so a run of 7
  x87 instructions between integer loop control (about 2040 exits per call).
- **lpoly:** a degree-12 polynomial by Horner's rule at 256 points: one long x87 run per point (about 257 exits per call).

The native build is arm64 with Apple's 64-bit `long double`, so it does less work at lower precision: its time is a floor, not an
equivalent, and its checksum differs. 5 rounds, median of the warm runs per call; load average 52.2 at the start (1, 5, 15 minutes:
52.17 53.07 37.98) and 31.4 at the end, thermal state 1 at both ends: a very busy machine, and the spread is wide.

| Workload | Native (double) | Process, loop | Process, call | vCPU, loop | vCPU, call | EPYC x87 (reference) |
|---|---|---|---|---|---|---|
| ldot | 4912 ns | 1518874 ns (309) | 1421398 ns (289) | 6793761 ns (1383) | 6939258 ns (1413) | 24972 ns |
| lpoly | 359 ns | 873306 ns (2430) | 951296 ns (2647) | 1631420 ns (4540) | 1646520 ns (4582) | 3702 ns |

- The EPYC column is the same source built with gcc for Linux and run on that CPU (`workload_main.c` in raven-macos-bench, median of
  7 runs): a different machine, given only to show what the x87 work costs on x86 itself.
- **What dominates** (INFERRED from the numbers above and the core timings): per exit about 0.7 µs in this process and 3 µs in a
  vCPU, plus about 90 ns per x87 instruction (decode and core). ldot is exits; lpoly is mostly decode and core. Exactness is a small
  part (the doubles mode saves about 45 ns per instruction).
- **What would help, not done:** keeping the decoded x87 runs instead of decoding at every exit, emitting loads, stores and fxch
  inline, and calling the core without an exit (the final form above). These belong to the generator work.

## Open items

- **Transcendental instructions** (fsin, fcos, fsincos, fptan, fpatan, f2xm1, fyl2x, fyl2xp1): not implemented; a block ends before
  them as unsupported. 31 instances in `libmingwex.a`, none in the DLLs or Notepad++. The oracle already records the EPYC's results
  (400 cases); an implementation needs a reduction of the argument modulo pi to beyond 64 bits and documented error bounds against
  those results, since AMD's and Intel's microcode need not agree to the bit.
- **fbld and fbstp:** decoded, not run (not found in the corpus outside data).
- **fscale with a huge ST(1) and OE or UE unmasked:** the scale is clamped to 2^20, beyond what the wrap by 24576 brings back into
  range, so the register then holds a wrong value. Masked (the only response the oracle exercises with such scales) the result is
  right.
- **Segment and 32-bit address forms** in x87 memory operands are not tested (see how it runs).
- **The silicon results file** must be written again from new runs (`silicon_overrides.py`) whenever `x87.py` changes; a stale file
  is refused by its Rosetta fingerprints, not silently applied.
- **#MF:** a waiting instruction with an unmasked exception pending stops the guest with `ExitReason::fault`; Windows would raise
  `STATUS_FLOAT_*` through SEH. No CONTEXT mapping of the x87 state exists yet either.
- **Guest addresses in the host core:** a memory operand at an unmapped or protected address is read or written by the host: in this
  process a fault there is a host crash unless the fault handler takes it, in a vCPU `Vm::read` and `Vm::write` throw out of the
  run. x86 would raise #PF in the guest. Not handled, including an access that spans two mappings and an fnsave or fnstenv left
  half written by a fault part way.
- **Running inside the guest** (after the AVX work): SSE4.2's string compares exit to the host the same way and belong to the same
  work (sse.md measures their exit).
- **Ordering:** x87 stores from the host are plain stores (in a vCPU through the host alias); TSO across guest threads for them is NOT
  verified.
- **FIP, FDP, FOP** are kept at 0 and fnstenv and fnsave write 0 there; software that reads them (some exception handlers) sees 0.
- **fxsave and fxrstor** (0F AE /0, /1) are not decoded as x87 and stay unsupported; MXCSR there would need folding as stmxcsr does.
- **MMX** is not implemented (designed for above); 32-bit code is out of scope.
- **Cost:** every run of x87 instructions is an exit and a decode per instruction (performance check above).
- **Writes to translated code** by an x87 store go through `GuestMemory::write`: `VmProcess::write` drops the translations of a
  watched page, and in this process `TestProcess::write`'s store faults on a watched page and its handler does the same (INFERRED from
  the code; no test stores into code with x87).
- **The Linux build** was not run (NOT verified); the core uses `unsigned __int128` and C++20 (`using enum`, `<bit>`).
